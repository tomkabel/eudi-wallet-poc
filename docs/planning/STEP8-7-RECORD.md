## What landed

### 1. DCQL parses `mso_mdoc_zk` (`verifier/go/oid4vp/dcql.go`)

- `Single()` accepts `format` `mso_mdoc` and `mso_mdoc_zk` (new constants
  `FormatMsoMdoc`/`FormatMsoMdocZk`); anything else is still refused.
- `Meta` gains `ZkSystemType []ZkSystemTypeSpec` and `VerifierMessage string`,
  with JSON tags matching the de-facto wire exactly: `system`, `id`,
  `circuit_hash`, `num_attributes`, `version`, `block_enc_hash`,
  `block_enc_sig` (analysis doc §2, taken from multipaz 0.99.0's source).
  `verifier_message` is carried and never acted on: an instruction a verifier
  sends is not a rule this verifier obeys from the wire.
- For `mso_mdoc_zk`, `Single()` requires `meta.doctype_value` AND a non-empty
  `meta.zk_system_type` — a query with no advertised circuit cannot be
  allowlisted, so it is malformed rather than merely unanswerable.
- `ZkAgeQuery(id, doctype, namespace, element, circuit)` is the `mso_mdoc_zk`
  form of `AgeQuery`: one credential, one claim, and a single
  `zk_system_type` entry built from a registry `Circuit` via `SpecID()`, so the
  advertised id and hash are the verifier's own facts, not caller-typed strings.

### 2. The circuit allowlist keys on the advertised `zk_system_type` (`oid4vp.ZkSystemTypeAllowlist`)

- Every advertised entry must match a registry `Circuit` on **all** of
  `id` (= `SpecID()`), `circuit_hash`, `version`, `num_attributes`,
  `block_enc_hash`, `block_enc_sig`; the `system` label must be one of the two
  strings the de-facto carrier actually uses (see finding 1 below). All
  entries are checked, not just the first: a query advertising one accepted
  and one unknown circuit is refused in full.
- The check runs BEFORE any FFI work: the match is against published registry
  entries only and `zk.CircuitHash` (an FFI call) is never invoked — the same
  discipline as the ISO path's session-spec allowlist (§5.3 rule c) and the
  registry's S11 inversion fix.
- Refusals surface as HTTP 403 ("circuit is not in the accepted set") from the
  presenter's `checkZk`. No running server reaches it yet: `/present/new`
  issues only `mso_mdoc` queries (`verifier/README.md`, "What this does not do
  yet"), so the path is library-level and test-driven.

### 3. The OpenID4VP response path verifies `zkDocuments` (`oid4vp/vptoken.go`, `present.go`)

- `VPToken.ParseZkVPToken` reads `vp_token[<credential id>]` as base64url CBOR
  and decodes it with the existing strict parser (`ParseZkDocumentsBytes`, the
  exact shape step 2a pinned against multipaz 0.99.0's serialization). The
  holder-supplied bytes keep the ADR-002 discipline: every deviation from the
  expected shape is a refusal, never a fallback.
- `MatchQueryZkDocument` picks the one zkDocument answering the query: zero
  documents is a nil answer (the wallet presented nothing provable — an
  answer, not an error, served 200 `valid:false`), more than one is refused,
  and the doctype must match the query.
- The server's `check` (`present.go`) dispatches on the session query's format;
  `mso_mdoc_zk` sessions route to `checkZk`, which walks the ISO path's rule
  order: advertised-circuit allowlist (before any FFI), per-zkDocument rules
  (unsolicited `zkSystemId` → 403; timestamp through the ISO path's
  `CheckTimestampWindow` window), trust-store-only issuer selection
  (`msoX5chain` selects, never adds), then `zk.Verify` with **the session's own
  B.2.6.1 OpenID4VPHandover transcript** (`Session.Transcript()`: client_id,
  nonce, response_uri from the stored session, never from the wire) and the
  document's own timestamp as `Now`. A proof that does not verify is an
  answer at 200 `valid:false`, not a 4xx.
- `Store.NewWith` exposes the pinned-parameter session constructor (caller
  supplies client_id, nonce, response_uri) for interop tests; `New` keeps
  generating nonces for production.

### 4. The fixture (`verifier/go/zk/testdata/step8-7-openid4vp-zk/`)

Generated by the fork's `:zk-conformance` module
(`Step87OpenID4VPFixtureTest`, branch `step8-7-fixture`) through multipaz
0.99.0's real serialization (`buildDeviceResponse` + `addZkDocument`), with the
proof bound to the B.2.6.1 OpenID4VPHandover transcript the test builds itself:

```
SessionTranscript = [null, null, ["OpenID4VPHandover", h']]
h' = SHA-256(cbor([client_id, nonce, null, response_uri]))
```

`request.json` records the handover parameters, the doctype/namespace/element,
the circuit tuple and the proof-bound timestamp, so the Go test re-derives the
transcript from the session parameters instead of trusting a shipped blob.
Files: `device_response.cbor` (360 859 bytes, proof 360 180 bytes),
`device_response_issuer.json`, `request.json`, `GENERATED-BY`.

## Findings

1. **The de-facto carrier's `system` string is `longfellow-libzk-v1`, not
   `org.iso.mdoc.zk`.** multipaz-longfellow-jvm 0.99.0's
   `LongfellowZkSystem.getName()` returns `longfellow-libzk-v1` (verified in
   the bytecode and in the generated fixture), while the ISO dcapi
   DeviceRequest this repository offers names the same system
   `org.iso.mdoc.zk` (isodcapi.go `BuildZkSystemSpec`, consumed by the step 2a
   fixture). Both are accepted as `zk_system_type.system` labels; the
   allowlist keys on `id`+`circuit_hash`+params, so the label is not a trust
   anchor. The profile picks `longfellow-libzk-v1` (profile rule 4), and
   `ZkAgeQuery` advertises it: stock multipaz resolves the query's `system`
   through `ZkSystemRepository.lookup`, which matches only that name.
2. **The B.2.6.1 transcript construction is confirmed against multipaz, host
   side.** A multipaz proof generated over the hand-built
   `[null, null, ["OpenID4VPHandover", sha256(...)]]]` transcript verifies
   under this repository's Rust runtime (first check anyone has done of these
   bytes, per the plan's note on SUNET's caveat), and does NOT verify over the
   ISO dcapi transcript. Both directions are asserted, here and in the fork's
   fixture test. The plan's PENDING-DEVICE interop item (real wallet vs real
   verifier over HTTP) stays open; this closes only the byte-level question.
3. **The proof is ~360 KB** (360 180 bytes), matching §23 item 24's
   expectation that `direct_post.jwt` is needed for this carrier on any
   size-constrained response mode. Measured, not assumed.

## Tests (`verifier/go/step8_7_openid4vp_zk_test.go`, package main, because it drives the presenter's `checkZk` and `zk.Verify` together)

- `TestStep87OpenID4VPZkVerify` — reads the fixture, rebuilds the session from
  `request.json`'s handover parameters, and walks the exact `checkZk` path:
  parse the vp_token, match the query, allowlist the advertised circuit,
  select the issuer, verify over the re-derived B.2.6.1 transcript. PASS;
  one flipped proof bit fails; the ISO dcapi transcript (step 2a fixture's
  binding) fails for the same proof.
- `TestStep87UnregisteredCircuitRefusal` — a query advertising an unregistered
  `zk_system_type` is refused (also: mixed accepted+unknown, tampered
  `circuit_hash` under a real spec id, and a `zk_system_type`-less query is
  malformed at `Single`); the accepted circuit passes and resolves to the
  registry entry. PASS, no FFI involved.
- `TestStep87UnansweredSession` — an empty DeviceResponse is a nil answer; a
  doctype mismatch is a refusal. PASS.
- `TestStep87HandleResponse` — POSTs through `handleResponse` into `checkZk`
  over httptest: the fixture as-is is 400 (timestamp window), an unlisted
  `zkSystemId` with the same stale timestamp is 403 (so that refusal precedes
  the window and `zk.Verify`), and the real proof re-wrapped under a fresh
  timestamp reaches `zk.Verify` and is 200 `valid:false`. A positive over HTTP
  needs a clock seam: the proof binds 2026-09-24T14:19:58Z. With the window
  check removed, the fixture comes back 200 `valid:true`. PASS.
- Full suite: `gofmt -l .` clean; `go vet ./...` clean; `go test ./...` green
  (verifier/go main 18.1 s incl. the three new tests, zk, oid4vp,
  internal/cborsub all ok).
