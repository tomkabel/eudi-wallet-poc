## The constraint that shaped the design

The Longfellow sig circuit does not parse the deviceSignature, it **verifies**
it: `signature_input_of_parsed_mdoc`
(`longfellow-zk/rust/applications/mdoc_zk/circuits/src/signature/concrete.rs`)
feeds `device_pk`, `device_sig_e/r/s` into the ECDSA relation, with
`device_sig_e` = SHA-256 over the COSE_Sign1 DeviceAuthentication structure the
runtime rebuilds (`mdoc.rs` `compute_transcript_hash`). A mint that holds only
the holder's public half therefore cannot produce a signature any prover would
accept — an all-zero signature fails `parse_signature`'s scalar range check
inside the circuit before any proving starts.

So `--device-public-key` mints a **placeholder** deviceSignature (64 zero
bytes, right shape, provably not a signature) and the holder re-signs
DeviceAuthentication with the real WSCD key at presentation time. That is not
a workaround; it is the production flow — a real wallet signs the live session
transcript at presentation, never at issuance, and `wallet/present.py`
`resign_device_auth` already does exactly this on every demo run.

## Implemented

### 1. `mint_ee_poa.py --device-public-key` (F12)

- `load_device_public_key` accepts SEC1 uncompressed hex with or without the
  `0x` prefix (`0x04||x||y`, or bare `x||y` — the two-coordinates form a wallet
  exports) or a PEM SubjectPublicKeyInfo. Non-P-256 keys are refused with
  `SystemExit` (the circuits bind 32-byte field elements; nothing else can be
  proven over). Curve identity is checked by name, not struct equality —
  `cryptography`'s curve singletons do not compare equal to a fresh
  `SECP256R1()`.
- On this path the mint generates no device key: `MSO.deviceKeyInfo.deviceKey`
  carries the holder's coordinates, the minted deviceSignature is
  `zero_device_sig()` (64 zero bytes), and the per-attestation output is
  `device_public_key.pem` (the public half the attestation binds) instead of
  `device_key.pem`. The private half is never imported (EE-SEC-003).
  `--batch N > 1` with `--device-public-key` is refused: one holder key shared
  across a batch would make its attestations linkable (EE-POA-010).
- `--over` default is `[18]` (was `[16, 18, 21]`, S10): the default output is
  exactly the §9.2 v1 element set — `age_over_18`, `issuing_country` `EE`,
  `issuing_authority`, `expiry_date` — with `age_over_16`/`age_over_21`
  opt-in. Validity stays 90 days, coarsened to midnight UTC (EE-POA-012); no
  status reference is emitted, matching §9.2.
- The 4-element default MSO is 436 bytes — still above the 256-byte floor the
  circuit imposes, so the mint's own guard stays satisfied with no padding.
- `issuer/README.md` updated (new sample output, the flag, and the
  placeholder-and-resign contract).

### 2. Trust store for both doctypes

- `verifier/go/zk/testdata/step6-device-pubkey/issuers.json` is the mock
  issuer's public key under BOTH `ee.riik.poa.1` and `eu.europa.ec.av.1` —
  EE-POA-003 issues both from the same authoritative source in one issuance
  transaction, so one key legitimately serves both doctypes. A comment in the
  file says why.
- The consuming code (`oid4vp.LoadTrustStore` → `TrustStore.Select`,
  `present.go` `check`, `iso.go` `selectIssuer`) needed **no changes**: it is
  already keyed by doctype with multiple issuers per doctype, and
  `Select`/`For` look up by `doc_type` only. Step 6's trust-store item is data,
  not code — the new tests pin the data.

### 3. Fixture: `verifier/go/zk/testdata/step6-device-pubkey/`

Generated by a throwaway script (kept out of the tree; the commands are in
`GENERATED-BY`): fresh holder P-256 keypair in memory →
`mint_ee_poa.py --out <tmp>/cred --over 18 --device-public-key 0x…` →
re-sign DeviceAuthentication with the holder's private key over the minted
transcript (the `resign_device_auth` bytes, copied from `wallet/present.py`) →
`ee_poa_demo <tmp>/cred age_over_18` (longfellow-zk at `LONGFELLOW_REV`,
circuit 8d0792…182121, `PROVE 359604 bytes`, `VERIFY Ok("ok")`, negative
controls refuse) → copy `mdoc.bin`, `transcript.bin`, `params.txt`,
`issuers.json`, `vector.json`, `issuer_dsc.pem`, `proof.bin`, `request.json`
plus `device_public_key.pem` and `GENERATED-BY` into the testdata directory.

The holder's private key was generated for the run and never written to disk;
the committed directory carries the public half only. That is the acceptance
point of F12: the fixture attestation is bound to a key whose private half
this repository does not hold.

The `ee_poa_demo` prover reads the doctype from `params.txt` (line 4), so the
plan's "if it is hardcoded to ee.riik.poa.1 already" note resolved to: not
hardcoded, but parameterised — no prover change was needed.

### 4. Tests

- `verifier/go/zk/step6_device_pubkey_test.go`:
  - `TestStep6DevicePubKeyFixture` — loads the fixture through the same
    `loadFixture` the step 0 test uses, asserts doctype/namespace/attr are the
    §9.2 v1 set, checks the registry first (EE-ZKP-023), asserts the minting
    issuer key is in the fixture trust store, verifies the proof through
    `Verify` (the C ABI into the Rust runtime), and refuses a one-bit-flipped
    proof.
  - `TestStep6TrustStoreCarriesBothDoctypes` — the fixture trust store carries
    the mock issuer key and only that key under both doctypes.
- `verifier/go/oid4vp/trust_test.go` — the real store:
  - `TestStep6TrustStoreSelectsFixtureIssuerForBothDoctypes` —
    `TrustStore.Select` accepts the fixture's issuer key for
    `ee.riik.poa.1` and for `eu.europa.ec.av.1`, with matching
    namespace/`doc_type` on each entry.
  - `TestStep6TrustStoreRefusesForeignIssuerKey` — the step 0 fixture's
    issuer key (a different, untrusted key) is refused for both doctypes.

The zk test pins the fixture data with a local struct in
`step6_device_pubkey_test.go`; the authoritative `TrustStore` behaviour is
tested in `oid4vp` (`trust_test.go`) — same file, both angles.
