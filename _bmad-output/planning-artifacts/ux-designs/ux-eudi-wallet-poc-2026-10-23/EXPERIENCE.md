# eudi-wallet-poc — Experience Spine

> Four surfaces, one release: the shipped sandbox site (behavioural spine added), the Android wallet's four consent-gate surfaces, the EU AV-Profile conformance report, and the Estonian relying-party acceptance kit. Identifier scheme is the PRD's own (`UJ-1…UJ-5`, `FR-1…FR-48`, `NFR-1…NFR-17`, `SM-1…SM-9`, `CM-1…CM-7`, `PG-1…PG-7`, `SG-1…SG-6`, `NG-*`, `OQ-*`, `OR-*`), kept distinct from `epics.md`'s `FR1–FR66` / `NFR1–NFR10`.

## Foundation

Four surfaces, two forms, two visual worlds. `DESIGN.md` (this run's) is the visual identity reference; repo-root `DESIGN.md` is the canonical identity for the sandbox surface, imported by reference and untouched by this release. These two spines win on conflict with any mock, wireframe or imported file, and repo-root `DESIGN.md` wins over this run's `DESIGN.md` on the sandbox's visual identity. No mockups or wireframes exist in this run yet, and `imports/` is empty: the four consent-gate surfaces and the conformance report are the key-screen candidates, so until those land the gates and the report exist as spine only.

| Surface | Form | UI system | What this release does to it |
|---|---|---|---|
| Sandbox site | Static HTML/CSS/JS served by a Python standard-library server; no framework, no build step | Root `DESIGN.md` — TEDI-derived, ria.ee chrome, Roboto + Material Symbols | Behavioural additions only: the typed tri-state (refusal / cancellation / retryable error) and the FR-34 degraded-boot page. No visual change |
| Android wallet | Kotlin, Jetpack Compose, JDK 17; installed for a device with `:app:installLocal_mocks` | Compose Material 3 (`ui/theme/WalletTheme`), platform-conventional | The four consent-integrity gates FR-45…FR-48 — the release's main UX work |
| AV-Profile conformance report | Generated self-contained HTML artifact, committed to the repo, regenerated by the runner on every run | Root token family, by reference | New surface |
| Relying-party acceptance kit | Go deployment profile plus its reader-facing surface; one documented install path, four acceptance cases | Root token family, by reference | New surface |

**Wallet platform position, recorded as a constraint rather than a visual decision:** the app ships a light colour scheme only. `WalletTheme` accepts a dark flag but always passes `LightColors` to `MaterialTheme` (`ui/theme/Theme.kt:52,65`); a dark-theme *preference* exists end-to-end and is honoured only by `MainActivity` (`MainActivity.kt:95-103`), while `PinActivity` and `DigitalCredentialsActivity` bypass it with `isSystemInDarkTheme()`. This is a technical constraint to flag to `bmad-architecture`, not a visual identity to re-spec here.

**Out of scope — no screens are designed for:** proximity Tier-2 ZK, the Art. 5a(4)(d) consent/activity dashboard (`EE-PRI-014`, deferred with PG-5), status lists and revocation surfaces, real-issuer onboarding, the circuit-registry service, statutory thresholds beyond 18, and an EU-level certification flow.

**Backlog position, stated because it changes nothing about the design but everything about tracing it:** two of the four surfaces have no `epics.md` story at all — the sandbox site, and all four wallet consent gates (the backlog predates the PRD and says so: `epics.md:52-56`, `:185-190`). FR-47's lockout and FR-45's unverified-requester messaging have no research-corpus backing either; the PRD is their only source. Do not cite a story id for these four gates.

## Voice and Tone

Microcopy. Brand voice and aesthetic posture live in `DESIGN.md` (this run's, and repo-root `DESIGN.md` for the sandbox).

| Do | Don't |
|---|---|
| Name the failed lookup: the register, the certificate chain, the trust anchor, the circuit list (PG-6, NFR-3) | "Something went wrong." |
| Use the three words the product already has — refused, cancelled, failed — and keep them distinct on every surface (FR-26, NFR-14) | One message for all three states |
| State the claim's scope where the claim is made: one boolean, one attestation, two carriers, and its limits (NFR-15, FR-40) | A claim that travels without its limits |
| Keep the shipped figure caption's rule everywhere: "These figures were measured just now, during your own run." (`sandbox/static/app.js:56`) | A number with no run behind it |
| Say `PENDING-DEVICE` or "unmeasured", with the reason (NFR-2, NFR-7) | An estimate presented as a result; a range presented as a commitment |
| Say who this is not: the independence notice, in both languages on the site and the kit, once on the report | Any implication of RIA, Ministry or EU endorsement |
| Say which carrier is mandated (Digital Credentials API) and which is profiled but unofficial (OpenID4VP `mso_mdoc_zk`) (OQ-6) | A label that lets a reader infer EU endorsement of the profiled carrier |
| Keep the existing consent strings' register — `presentation_verified_party` ("Verified party" / "Autenditud osapool") — and add the unverified counterpart in both complete locales | An empty requester line above a badge; a name asserted without a validation behind it |
| Tell the user what the shop learned and what it did not, as plainly on the wallet as on the page | Overstating the privacy position (PG-5, FR-42: no unobservability claim) |
| Write the kit's own hard truths into the kit: SM-3 and SM-4 unachieved, results self-produced | Putting an unachieved metric in a release note and leaving the reader to find it |

Compliance vocabulary is banned everywhere on every surface — "conformant", "certified", "compliant", "meets the profile" (`make check` fails on it, FR-36, NFR-1). So is the vagueness that replaces a claim with silence: going quiet where a claim was made is itself a failure (CM-5).

## Component Patterns

Behavioural. Visual specs live in `DESIGN.md.Components` (wallet, sandbox additions, report, kit). The four consent gates are the heart of this section.

### The four consent gates (FR-45…FR-48)

| Component | Use | Behavioural rules |
|---|---|---|
| Requester identification (two-state) | Remote consent, proximity consent and its no-match variant, DC API consent, credential offer, mock-PID consent | **FR-45.** The `readerAuth` chain is validated to a trust anchor **before any requester name renders**; an unvalidated name is never rendered as verified. On failure the component renders the unverified state, names the validation failure (no trust anchor configured / unparseable chain / name mismatch), offers **only Refuse and Cancel**, and keeps the chain's failure point behind a disclosure. The proximity path's requester name — never assigned today (`ProximityViewModel.kt:474`), so the screen renders an empty headline above an unconditional badge — gets the same two-state treatment. The DC-API surface's honest-but-hidden code comment (`DigitalCredentialsScreen.kt:153-157`, whose certificate trust is not validated there) becomes the user-facing state. The unconditional badge is removed from all five render sites (`components/VerifiedParty.kt:18-31`) |
| Verification-cause disclosure | Inside the unverified state | A disclosure affordance, closed by default; opening it reveals the failure point in machine terms (the chain, the missing anchor, the mismatched name) and nothing beyond it. It is not certificate internals by default, and it never offers a next step other than Refuse/Cancel |
| Consent card (one component) | Presentation (remote) and proximity | **FR-48.** One component renders both paths; the consent card internals duplicated today (`ProximityScreen.kt:203-268` vs `PresentationRequestScreen.kt:398-489`) are unified so "the same terms" is achievable in one place. Both paths state what is shared and with whom, list the fields, and carry the same notice set — the channel notice, the tier and last-attestation notices, the footer note — with the requester's verification state first. Nothing is emitted before the gate passes |
| Refusal block | Any surface where a request is refused | Names its cause, offers no proceed path where the refusal is a hard one, and is rendered with a state word so it does not rely on colour. Distinguishable from cancellation and from a retryable error in the UI, in the log and in the acceptance cases (FR-26, NFR-14); the log records the reason and no attribute value (OR-4) |
| Predicate and policy refusals | Consent and pre-consent | At most one age predicate per presentation (FR-4); more than one is refused; a predicate held `false` is never transmitted — the user is told and the counterparty receives the no-match answer (FR-5, PG-3); weaker requests are refused before consent with the reason shown and the tier labelled (FR-6); a missing credential in a multi-credential session fails the session naming it (FR-7, UJ-4) |
| Presence prompt | Proof generation, plain presentation, signing | **FR-46.** The platform user-authentication prompt's result is what the key operation depends on — not an application-level flag. Today the prompt is bound to the key through a `CryptoObject` (`ui/prompt/PromptDialogHost.kt:89,140`) and fails closed, but it sits *behind* the app-level PIN gate with nothing explaining it, its reason copy is English-hardcoded (`PromptDialogHost.kt:156-159`), and a cancelled prompt aborts the flow silently on the proximity path (`ProximityViewModel.kt:378-380,419-426`). Each key operation carries the gate, or the ungated path is removed rather than left reachable. Any operation attempted without it fails |
| Consent gate (PIN) | Presentation, proximity, issuance, and the mock consent run *[NOTE FOR UX: Open Questions 5 — the framework-launched DC-API surface's gate wiring is undecided.]* | The existing app-level gate, kept, with its copy and its counter re-wired (below). It is not a substitute for the presence prompt and must not be presented as one |
| Attempt counter | On the consent gate | **FR-47.** Remaining attempts are read from the persisted record (`PinVerifier` — 5 attempts, 30-minute lock, written before the answer is returned) and shown as a plain remaining-count line using the existing copy shape. The in-memory counter that stops at 3 and is re-created on every `PinActivity` launch is removed, and so is the simulated `delay(1000)` "remote check" (`PinEntryViewModel.kt:26,130-131,194-208`) |
| Lockout surface | Raised when the persisted lock is in force; consulted at launch | States the lockout duration and the escalation path, offers the one action that remains, and is the only surface a locked user sees. *[NOTE FOR UX: Open Questions 3 — the escalation wording is not in the record.]* A locked record refuses even a correct PIN (`PinVerifier.kt:51-53`), so the surface must never say "incorrect PIN" to a locked user. State survives process death and app relaunch; relaunching does not reset the count |

**Two recorded discrepancies the design must not paper over.** (1) The proximity path is *already* PIN-gated in this checkout (`ProximityScreen.kt:82-88`, `ProximityViewModel.kt:340-365`, commented "D12 (mobile F8): the share is PIN-gated"), while FR-48's text says it emits with no gate at all — the parity work is the content set and the unverified requester, not adding a gate where one exists; a PRD correction is suggested after this run lands. (2) The proximity path has no reader trust anchors configured, so **every** proximity reader is unauthenticated today (`ProximityViewModel.kt:257-258`, `:265-266`): on that path the unverified state is the normal case, not the exception, and the copy must read as normal-case treatment rather than as an incident.

**Two gaps recorded, not filled here.** *[NOTE FOR UX: Open Questions 1 and 2 — the offer and mock-PID surfaces' requester treatment, and the back-to-back gate explanation.]* The credential-offer and mock-PID surfaces display a name with no validation input at all (`CredentialOfferScreen.kt:111-129`, `PidAuthenticationScreen.kt:46-51` — the latter hardcodes `tara.ria.ee`). And the presence prompt's reason strings for multipaz's own `PresentmentUnlockReason` come from multipaz's localized resources, which this app cannot override (`PromptDialogHost.kt:151-154`). See *Open Questions*.

### Conformance report

| Component | Use | Behavioural rules |
|---|---|---|
| Front summary | Top of the report | Counts of clauses by state and the run's verdicts, produced by the run that just happened. Failures are counted; a summary that reports only passes is not a summary |
| Clause row | Clause list | One row per clause in the AV-Profile's own sequence. A clause resolves to a test id **or** to an explicit "out of scope for v1" note with a reason, and the out-of-scope rows sit adjacent to the covered ones in natural position — never in a footnote (FR-16, CM-1) |
| State label | Every clause | A word: what the test did, in the environment the report names. `ERROR` and `NOT_EXECUTED` are their own states and are never rendered as a pass (the same rule the runner stories already carry) |
| Fail-closed reporting | Any clause whose evidence is missing | A clause with no test is reported as not evidenced, never as satisfied; the report never substitutes a neighbouring result |
| Reproducibility block | Foot of the report | Names the commit, the profile revision, the host class and the commands; states that Python inputs are pinned and that the Rust toolchain is not, so it is named rather than implied (NFR-4, NFR-8, NFR-14) |
| Independence notice | Report shell | Text only, at the top, before the summary |

### Relying-party acceptance kit

| Component | Use | Behavioural rules |
|---|---|---|
| Install path | First surface | One documented path, commands copyable, no undocumented step; the deployment profile runs over the existing verifier rather than forking it (FR-21) |
| Case card | Four cases | PID wallet, AV-attestation wallet, unattested ZK request, unregistered relying party (FR-25). Each is self-contained and re-entrant: it restates its own preconditions, expected verdict, refusal cause and the log line to expect, so a reader who fails case 3 does not re-read cases 1–2 |
| Outcome states | After a case runs | Three distinguishable states, the same three the rest of the product uses: refused (with the cause named — for the unregistered-relying-party case, the register is named as the cause), cancelled by the operator, failed and retryable (FR-26, NFR-14) |
| Register lookup | Any case that needs it | Pluggable, mocked, fail-closed: an absent, unparseable or ambiguous entry refuses, the refusal names which lookup failed, and the cache's staleness is explicit and logged (FR-23, PG-7) |
| Honesty block | Where the cases are read | SM-3 and SM-4 are unachieved at v1 and the kit says so: no Estonian service owner is engaged, the integrator count is zero, and any maintainer-produced result is labelled self-produced (CM-2). This is the surface's licence to exist without a support channel: a stranger must be able to diagnose a failure from the case itself (OR-6) |
| Language toggle | Every kit surface | Estonian first with an English toggle; every string in both |

| Clause out of scope for v1 | Clause row, in profile position | Its own state **plus its reason**, adjacent to the covered clauses (FR-16) |

## Interaction Primitives

**Wallet.** Tap to act; the system back gesture; the platform biometric/user-authentication sheet for key operations; the app's own numpad for the PIN; per-attribute switches for the fields being shared; the camera for QR scanning; BLE for proximity.

**Sandbox.** Click or tap to advance; keyboard operation of the rail (the current step is marked with `aria-current` and its own `tabIndex`), the anchors in the masthead, and the log's disclosure; the ET/EN toggle; reduced motion honoured.

**Report and kit.** Keyboard-complete: every clause row, every case, every control reachable in order with a visible focus state; disclosures opened with the keyboard; nothing hover-only; nothing that requires colour to be read.

**Banned on every surface:**
- A proceed-anyway path past an unvalidated requester, or a requester name rendered as verified without a validated chain (FR-45).
- An application-level flag standing in for the platform presence prompt on a key operation (FR-46).
- Resetting the attempt count by relaunching, or a simulated remote check, or a "remote check" delay standing in for a real policy (FR-47).
- Silently downgrading a presentation, or answering with a neighbouring threshold, or transmitting a `false` predicate (PG-3, PG-4).
- Rendering a not-built or not-run state as a simulated result (FR-34).
- A scripted animation where a real attack outcome belongs (FR-30).
- Colour as the only carrier of a state; a footnote for a shortcut; a status colour filling a region.
- Compliance, conformity, certification or assessment vocabulary anywhere (NFR-1, FR-36, NG-2).

## Accessibility Floor

Behavioural. Visual contrast lives in `DESIGN.md` (and, for the sandbox, in repo-root `DESIGN.md`'s pinned tokens).

- **Baseline.** WCAG 2.1 AA is the stated baseline on every surface; for the wallet the specification additionally makes Directive (EU) 2019/882 and EN 301 549 v3.2.1 a `SHALL` (`EE-ACC-001`–`EE-ACC-004`). **No EN 301 549 audit evidence exists yet** (risk R13) — no surface claims an audit, and the absence is stated rather than implied.
- **Keyboard-complete.** The sandbox (rail, anchors, disclosures, the language toggle), the report and the kit are operable without a pointer, with a visible focus state throughout. The wallet is a platform surface: TalkBack, switch access and the platform's own focus traversal.
- **Announcements.** Long-running steps announce progress and completion (the sandbox's live region already does this for phases and for the queue; the typed state blocks announce their state and cause). The new wallet states — unverified requester, remaining attempts, lockout, presence-prompt failure — are announced when they appear, not only when read.
- **No colour-only signalling.** Every status carries a word on the new surfaces: the report's clause states, the kit's outcomes, the wallet's requester states, the sandbox's tri-state blocks.
- **Reduced motion.** Honoured: the proof mark goes static (keep the shipped behaviour), the step reveal is not applied, scroll jumps are instantaneous. *[NOTE FOR UX: Open Questions 6 — the site's remaining ungated transitions are not decided.]*
- **Targets and focus order.** 48dp minimum on the wallet; focus order follows reading order on every surface; the consent gate's action row is the last thing reached and never traps focus.
- **Honest accessible failure.** An accessibility-relevant refusal (a camera or Bluetooth permission denied, a reader that cannot be reached) names its cause like every other refusal.

## Honesty and Claim Discipline

This section is the release's own constraint, not a tone note. It binds every surface and every figure.

**Vocabulary.** No artefact states or implies compliance, conformity, certification or assessment (NFR-1, FR-36, NG-2, NG-3). The permitted form is the one the backlog already carries: *these requirements are supported by these tests, in this environment*. A check fails `make check` on the banned words, and going vague instead of claiming is also a failure (CM-5).

**Numbers.** A number appears on a surface only if it came from the run that just happened (FR-28; repo-root `DESIGN.md`'s first Do). Every published figure states its baseline, method, assumptions and confidence; a range is never presented as a commitment; an unmeasured row says `PENDING-DEVICE` rather than being estimated (NFR-2, FR-37). v1 makes **no performance claim at all**, and every device row stays `PENDING-DEVICE` (PRD §6.2). Verification is stated as capacity on a named host class, never as latency, and the two published host figures must not be compared (NFR-6). Proving figures carry their host class (NFR-7). The kit's integration and time-to-first-verification metrics are unmeasured, and it says so (SM-3, SM-4, FR-27, OQ-10).

**Scope of the claim.** One boolean predicate, one attestation, two carriers, and the limits travel together: `ZKP_08`'s tension reported rather than resolved; the bundled circuits' 109-bit soundness declared against the recommended floor; no device measurements asserted (NFR-15, FR-40, FR-41). Attestation ordering is stated where it matters (AV preferred, EE-PoA fallback). Unlinkability is stated per path with a test behind it, and where it cannot be claimed it is recorded as not claimed (FR-42, DG-7).

**Truth of a screen's own claims.** A requester name shown at consent is a claim about authentication, so the screen must not make it until the chain validates (SG-2, FR-45). The consent screen shows the requester, the predicate and the channel before a proof exists (FR-10).

**Findings are published, not implied fixed.** The repository's own audit — 124 findings, none critical, taken at commit `732d57e` while the PRD describes `2d38feb` — is referenced by severity count with its commit stated, and no artefact implies a published finding is closed without a test or a tool run (SG-1, SG-4, NFR-16). The four gates in this release exist precisely because the audit's TIER 1 items were on advertised paths; the four negative tests, one per gate, are their evidence (SM-9, CM-7) — and a new refusal must name its cause, so the tests assert reasons, not merely refusals.

**What the surfaces must not do with the audit:** quote it without its commit; present the deferred items (signed authorization requests `EE-PRO-004`, `EE-PRO-010a`, supply-chain pinning, main-thread blocking, debug logging, the mock trust surfaces) as fixed; or let the removed behaviour (the per-launch counter reset, the simulated remote check) survive as documentation instead of being gone (FR-47).

## Independence and Branding

- **The notice, on every surface.** The sandbox carries it in three placements and two languages (utility bar, info alert, footer) and that stays root-owned. The report and the kit carry it in their own shells, before any result. The notice's job is to make "whose product is this not" answerable without leaving the page (NG-13, FR-33).
- **No state branding.** No RIA logo, no state coat of arms, no implied endorsement, on any surface, in any asset (FR-33, NG-13). The sandbox's wordmark is bespoke for exactly this reason. The wallet ships a funding logo (locale-overridden) and no state arms; how that logo reads against NG-13 is a placement question this run did not decide. *[NOTE FOR UX: Open Questions 4 — whether the wallet carries an independence notice, and where.]*
- **Carrier naming (OQ-6).** Where either carrier is named, the artefact says which is mandated and which is profiled: the Digital Credentials API path is the mandated transport the profile fixes; the OpenID4VP `mso_mdoc_zk` carrier is profiled by this project and is not a standard. No copy may present the ZK path as mandated over OpenID4VP, and no label may fuse the transport with the format in a way that overstates the standard's state.
- **Tier and authority.** A documented fallback is labelled where it happens (PG-4); a plain fallback is not offered as equivalent to a proof; the issuer chain's disclosure (`msoX5chain`) and the Tier-1 linkability limit are stated rather than hidden (glossary: *Issuer-chain disclosure*, *Linkability*).
- **Attribution of results.** Any result the maintainers produced is labelled self-produced; accept nothing else as external acceptance evidence (CM-2).

## Reference Points and Rejected Directions

**Lifted from the shipped project.**
- The sandbox's own identity and structure — the six-step rail, the ledger's two columns, the cheat band, the bilingual toggle as identity rather than utility — inherited whole, not re-designed.
- The wallet's existing *typed* refusal vocabulary in `docs/CONFORMITY.md` (a dedicated non-retryable message, logged reason, the negative answer sent in the background, the channel labelled, the subject shown only on a pass). The new refusal, cancellation and retryable states reuse those categories rather than inventing a parallel set.
- The wallet's existing durable lockout (`PinVerifier`: 5 attempts, 30-minute lock, persisted before the answer returns). FR-47's UI is designed onto the storage that exists, not beside it.
- TEDI / ria.ee chrome for the site, and Material 3 for the wallet — the ships-as-is postures.

**Rejected, with the reason it lost.**
- **Root token transplant into Compose** (rubric 32) — it would make the wallet a foreign body on Android and buy nothing the status bridge does not.
- **Pure platform defaults, no status pinning** (rubric 84) — nearest rival to the chosen stance, and it loses the one thing that must read the same on phone and page: what refused and what was cancelled.
- **A counter-silent lockout** (the rubric's own leader) — overruled on platform-convention grounds: Android users expect a remaining-attempts count, and the cap holds regardless.
- **An end-of-flow verdict screen for the sandbox tri-state** — a refusal that has to be walked to is not the refusal being advertised; the state belongs at the step where the run stopped.
- **A build-time or deploy-time not-built page, or a terminal-only message** — the visitor is the audience the requirement names, and only a served page can say it to them.
- **The report as Markdown in `docs/`, or as runner output only** — a reader has to be able to open it and a third party has to be able to regenerate it.
- **Outcome-ordered or surface-ordered clause lists** — both hide the out-of-scope clauses behind their ordering, which is the one thing FR-16 forbids.
- **English-only for the report *and* the kit** (the rubric's leader) — overruled for the kit, whose reader is an Estonian operator, in favour of the split stance stated per surface.
- **A sixth journey for the venue/proximity session** — on a ZK-capable device a proximity age request is refused, so there is no proof session to narrate; the refusal is the advertised behaviour and it lives in the open question (OQ-11), not in the journey set.
- **An assessor journey** — reproduction is a workflow with metrics and an NFR-8 duty, not a session a protagonist runs.
- **Compliance-language softening, and its twin, silence** — a claim replaced by vague words fails the check, and a claim replaced by nothing fails the intent (CM-5).
- **A fabricated result when the toolchain is missing** — the one thing the sandbox's own first Do exists to prevent.

## Key Flows

The five journeys are the PRD's own (§2.3, `prd.md:152-248`), quoted verbatim. Only their structure is made explicit here: each journey's path is split at its own clause boundaries into numbered steps, and no clause is added, dropped or reworded. Their protagonist names are the PRD's drafted placeholders (A-2), not narrated by a user.

### UJ-1 — Rasmus sees the proof before he believes it (sandbox)

**Persona + context.** "Rasmus, a journalist writing about state digital identity, has read claims about zero-knowledge age checks and does not trust claims."

**Entry state.** "No account, no phone, a desktop browser; arrives cold at the sandbox site in Estonian (the toggle offers English)."

**Steps.**

1. Picks a labelled test persona (synthetic name and birth date).
2. Registers it against the sandbox's Population Register.
3. Receives the age attestation.
4. Follows the step rail to the test shop.
5. The shop asks for `age_over_18`.
6. Watches the proof timeline fill while the clock counts.
7. Reads the ledger of what the shop learned against what stayed with him.
8. Clicks the sandbox's own "try to cheat" control.

**Climax.** "The ledger, both columns, each number from the run that just happened — and the tamper attempt failing in front of him rather than being described."

**Resolution.** "He has a reproducer he can cite; every step is repeatable, and the page's independence notice tells him whose product this is not."

**Edge case.** "The prover or verifier is not built on the host, so the guided flow cannot run; the site says so and names the documented command instead of showing a simulated result."

*Spine trace:* the degraded-boot page (FR-34), the typed state blocks (FR-26), the ledger and figures rule (FR-28/FR-29), the cheat band (FR-30), shortcuts named in flow (FR-31), bilingual (FR-32), the notice (FR-33), the accessibility baseline (FR-35).

### UJ-2 — Mari buys wine without handing over her birth date (record U1)

**Persona + context.** "Mari, a Tallinn resident who wants the order to go through and does not want another birth date copy in another database."

**Entry state.** "Authenticated to an Estonian online service; wallet installed and holding an age attestation; TARA-shaped session context established."

**Steps.**

1. The service asks for `age_over_18` over OpenID4VP with an `mso_mdoc_zk` DCQL query.
2. The wallet resolves the held circuit.
3. The consent screen names the requester and the channel.
4. She approves.
5. The proof is produced and encrypted to the relying party's published key (`direct_post.jwt`).
6. The verifier checks the transcript, the circuit allowlist and the proof.

**Climax.** "The order completes; the relying party's log holds a boolean and no attribute value."

**Resolution.** "Exactly one predicate was disclosed and the wallet labelled the presentation as ZK or as a documented fallback."

**Edge case.** "The relying party asks for a second age predicate, or for a predicate the wallet holds `false`; the request is refused or the no-match answer is returned, with a stated reason to the user, and no `false` predicate is ever transmitted."

*Spine trace:* this is where the four gates live — the requester's chain validated before the name renders (FR-45), the presence prompt on the proof (FR-46), the consent gate's persistence and copy (FR-47) — plus the channel notice and tier label (FR-6, PG-4), one predicate (FR-4), no `false` transmitted (FR-5, PG-3), the boolean-only payload (FR-10, PG-2).

### UJ-3 — Liis accepts a foreign proof her service has never seen (record U2)

**Persona + context.** "Liis runs the verification side of an Estonian service that has been told to accept other Member States' certified wallets."

**Entry state.** "Her service deployed against the O1/O2 artefacts; no Estonian wallet to test with; the accepted circuit set unpublished."

**Steps.**

1. A foreign AV-profile holder presents over the DC API.
2. The request carries the AV attestation with the `ZkSystemSpec` parameter tuple.
3. Her verifier resolves the circuit against its registry.
4. Validates the proof.
5. Returns a verdict, encrypted.

**Climax.** "A foreign proof verifies at her service without a birth date crossing the boundary, and the AV-Profile conformance run reports the same result for this fork's verifier and for an external implementation."

**Resolution.** "She can state which clauses she has evidence for and which she does not; a non-`longfellow-libzk-v1` system is refused."

**Edge case.** "The circuit registry is unreachable; the verifier fails closed and says which lookup failed instead of allowing the presentation."

*Spine trace:* the conformance report's front summary, per-clause states and adjacency (FR-11…FR-16), fail-closed reporting and the named failed lookup (PG-6, NFR-3), the external-implementation state (FR-19, SM-2), the refusal of another ZK system (NG-7).

### UJ-4 — Tanvi onboards without an isikukood (record U4)

**Persona + context.** "Tanvi is an e-resident opening an Estonian service account; she has no Estonian personal identification code and does not want her full date of birth on file."

**Entry state.** "Holds a PID and an age attestation; the service needs an attribute subset plus an age predicate in one session."

**Steps.**

1. The service asks for both credentials in one session.
2. The wallet answers both, with the age predicate proved and the PID attributes selectively disclosed.

**Climax.** "Onboarding completes; the session transcript carries no isikukood anywhere and the log names both credential identifiers."

**Resolution.** "The service holds what it asked for and nothing more; the wallet shows what was disclosed and to whom."

**Edge case.** "One of the two credentials is missing; the session fails with the missing credential named, rather than completing partially."

*Spine trace:* the per-credential disclosure list on the consent card, the presence prompt on both credential operations (FR-46), the multi-credential session state (FR-7), the isikukood never crossing the boundary (PG-1), and the activity log showing what was disclosed and to whom.

### UJ-5 — Sander gets his first successful verification (record U5)

**Persona + context.** "Sander is the integrator at an Estonian service operator; his deadline is the end-2026 acceptance window and his target is a service that answers "does this work?" honestly."

**Entry state.** "Nothing deployed; no register access; the sandbox's synthetic personas are the only test identities."

**Steps.**

1. Deploys the relying-party acceptance kit against the documented commands.
2. Runs the four cases (a wallet with a PID, a wallet with an AV attestation, an unattested ZK request, an unregistered relying party).
3. Sees each refusal name its cause.
4. Wires the register interface against the shipped mock.

**Climax.** "A first successful verification, with the time to it measured and reported, and a refusal that is distinguishable from the user having cancelled."

**Resolution.** "He has a proposal for the register interface instead of a guess, and a bounded, logged, fail-closed fallback for when the register does not answer."

**Edge case.** "The mock register is configured absent or the certificate names no intended use; the lookup fails closed and the refusal says so."

*Spine trace:* the kit's install path, four self-contained cases and outcome states (FR-21, FR-25, FR-26), the register interface proposal and mock (FR-23, FR-24), the fail-closed refusal naming the register (PG-6, PG-7), the measured time-to-first-verification — unmeasured at v1 and published as unmeasured (FR-27, SM-4, OQ-10) — and the kit's own honesty block for SM-3/SM-4.
